# 项目工作进度记录

用本 skill 把跨轮次协作变成可追溯的项目记录，而不是依赖对话上下文。记录应服务于下一轮继续工作：读者能够快速知道为什么做、看过什么、改了什么、验证到哪里，以及下一步缺什么。

## 记录文件

默认记录文件是当前项目根目录的 `.claude/work-progress.md`。如果项目已有不同名称的进度文件，优先沿用已有文件；不要创建重复记录。无法判断项目根目录时，先以当前工作目录和项目级 `CLAUDE.md` 为准。

每次触发时：

1. 读取项目级 `CLAUDE.md`（若存在）。
2. 读取 `.claude/work-progress.md`（不存在则创建）。
3. 读取本轮实际涉及的计划文件、源码、测试、配置或命令输出；不要仅凭上一轮总结猜测状态。
4. 在记录中追加本轮任务条目，或在同一轮已有条目中补齐“实际效果”和“验证结果”。保留历史，不覆盖已完成任务。
5. 如果本轮只讨论而未修改代码，明确写“未修改代码”；如果没有运行验证，明确写“未验证”。

## 固定记录模板

每个任务使用以下结构。简单任务也保留标题，但不必为了填表虚构内容。

```markdown
## YYYY-MM-DD｜任务标题

### 目的
- 本轮要解决的问题、业务目标和范围边界。

### 参考/阅读文件
- `相对路径`：为什么阅读，获得了什么事实。
- 外部计划或命令输出可写摘要，但不要复制敏感内容。

### 执行模块
| 模块/文件 | 为什么执行 | 执行前效果 | 预期执行后效果 |
|---|---|---|---|
| `path` | 原因 | 当前已确认行为 | 完成后应改变的行为 |

### 实际执行与效果
- **已完成**：只写已经由文件差异、命令输出或测试确认的内容。
- **进行中**：已经开始但未达到验收标准的内容。
- **未修改/未执行**：本轮明确未做的内容。

### 验证
- `命令或验证方式`：通过 / 失败（附关键错误）/ 未验证。
- 区分“已确认”“推测”“待验证”。

### 缺口、风险与下一步
- 尚未完成、前置条件、已知风险和建议的下一步。
```

## 事实与安全规则

- 先核对当前工作区、文件内容和命令结果，再写状态；不要把计划当成完成事实。
- 使用三种标签区分状态：**已确认**、**推测**、**待验证**。编译未运行时不得写“编译通过”。
- “执行前效果/执行后效果”写行为和可观察结果，不贴大段代码；涉及未实现部分，写清楚当前行为和目标行为。
- 参考文件列出相对路径、计划名和必要的符号；不要重复粘贴大文件。
- 不写入密码、Token、私钥、完整认证配置、签名 URL、完整凭证值、完整 MQTT payload 或其他敏感数据。用“已脱敏凭据”“任务 ID 摘要”等替代。
- 不擅自把业务推测写成需求；不擅自扩大任务范围。发现计划和实现不一致时，记录差异并提示用户。
- 不因为更新记录而修改业务源码、提交 Git、删除文件或执行外部发布操作。

## 任务开始与结束时机

- 在开始多文件/架构任务前，先记录目的、范围、参考文件和执行模块；执行前效果与预期效果必须先写入。
- 完成代码修改后，补写实际效果、未完成项和验证结果。
- 运行测试、构建、真机验证或发现失败后，立即补写结果和下一步，不等待任务结束。
- 用户询问“做到哪了”“还差什么”时，先读取记录并用当前代码/状态核对，再补充一条进度快照。

## 与自动钩子的配合

如果项目设置通过 `UserPromptSubmit` 注入本 skill 的提醒：

- 不要把钩子提示当成已经完成记录；仍需执行读取、判断和写入。
- 对需要修改文件的任务，先更新记录再改代码，结束时再补实际效果和验证。
- 自动钩子只负责提醒，不能根据关键词自动声称某模块已完成。

## 输出习惯

完成本轮后，用中文简要汇报：记录文件位置、已确认完成项、未验证项和下一步。不要把整个 Markdown 文件重复输出，除非用户要求。

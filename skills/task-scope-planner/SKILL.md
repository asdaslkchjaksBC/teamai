# 任务范围规划

在执行前，根据用户提示词生成范围明确的任务计划。这个 skill 只在主 Agent 内部使用，不拉起子 Agent，不注册自定义 Agent，不委托工作。

## 使用场景

当用户提出以下要求时使用：

- "规划一下", "先澄清", "范围收敛", "生成约束", "避免失控", "任务合同", "先别做"
- 将模糊提示词转换成明确工作计划
- 定义任务范围内和范围外的内容
- 区分事实、推断和待确认问题
- 在代码修改、提交、删除、重启、部署、远端变更、架构或重构任务前识别确认闸门

不要把这个 skill 强行用于简单命令、普通问答、直接状态查询，或已经明确且低风险的任务。

## 输出约定

输出规划产物，不输出实现。结果要简洁、具体、可执行。

使用这个结构：

```markdown
**任务理解**
...

**已知事实**
- ...

**缺失约束**
- ...

**建议范围**
范围内:
- ...

范围外:
- ...

**约束**
硬约束:
- ...

软约束:
- ...

禁止事项:
- ...

**风险判断**
...

**执行计划**
1. ...
2. ...
3. ...

**验证方式**
- ...

**确认点**
需要确认:
1. ...
```

如果提示词简单且风险低，只保留必要部分，不要套完整模板。

## 规划规则

### 1. 复述目标

用一到两句话说明用户真正想完成什么，并判断任务类型：

- 代码修改
- 重构或架构任务
- 排障或事件分析
- 基础设施或远端操作
- Git 操作
- 文档或纯规划
- 简单命令或问答

### 2. 区分事实和推断

只有用户明确输入和已验证的本地上下文可以作为事实。任何推断都必须标记为假设或待确认问题。

事实示例：

- 用户点名的仓库、路径、分支、文件、设备、主机、URL、账号、请求 ID
- 用户给出的硬性限制、提交文案、变体名、目标版本
- 当前命令输出或已经查看过的文件内容

推断示例：

- 某个行为归属哪个模块
- 改动应该是全局生效还是只限定某个变体
- 是否可以跳过验证
- 是否允许重启远端服务

### 3. 生成约束

将约束分成：

- 硬约束：必须遵守；不明确时不能进入实施。
- 软约束：偏好或权衡，用于指导方案。
- 禁止事项：没有明确确认前不能执行的动作。

默认禁止事项：

- 删除文件、配置、数据、容器、包或插件
- 执行破坏性 Git 命令
- 提交或推送
- 重启服务、设备、路由器、容器或生产进程
- 修改远端主机、线上端口、凭据、DNS、防火墙、路由或包部署路径
- 把点名的小范围改动扩大成宽泛重构

### 4. 收敛范围

始终说明：

- 范围内：满足提示词所需的最小工作
- 范围外：容易发散但不必要的扩展
- 灰区：需要用户确认的决策点

对于代码和架构任务，除非用户明确要求更大范围设计，否则优先选择保持行为不变的最小范围。

### 5. 判断风险

使用这个分级：

- 低风险：只读检查、简单命令、直接解释
- 中风险：本地编辑、本地构建、非破坏性配置变更
- 高风险：架构或重构、较大行为变化、设备或系统应用替换、远端操作
- 破坏性风险：删除、重置、重启、推送、生产路由变更

对于高风险或破坏性风险，停在计划阶段，先要求用户确认，不直接实施。

### 6. 生成计划

计划应包含：

- 上下文收集步骤
- 修改或操作步骤
- 验证步骤
- 停止条件
- 必要时给出回滚或恢复说明

不要对低风险任务过度规划。小任务一到三步即可。

### 7. 确认闸门

如果缺少以下关键值，需要要求用户确认：

- 目标仓库、路径、模块或文件
- 变体、设备或环境
- 是否允许修改代码
- 是否需要运行测试或构建
- 是否允许提交、推送、重启、删除或部署
- 验收标准
- 架构边界或权衡

需要确认时，以具体问题结尾。不要在同一次回复里继续实施。

## 风格

- 使用简体中文回复。
- 直接、具体。
- 优先使用短列表，避免长篇泛化说明。
- 不要发明约束并把它们包装成用户决定。
- 不要把这个 skill 当成通用项目管理模板；必须贴合当前提示词和真实上下文。
